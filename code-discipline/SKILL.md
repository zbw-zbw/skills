# AI 编码纪律

每次写代码、改代码时对照执行，交付前自查一遍。全部为硬约束；与用户当次明确指令冲突时，用户指令优先。

## 注释

- 只写代码本身表达不了的信息（为什么这么做、约束、坑、防回退提醒），一行内说清
- 禁止复述代码逻辑、改动过程说明式注释、多处重复同一说明
- 注释与代码一律不加 emoji；注释密度跟随周围代码

## 改动范围

- 只改任务要求的代码；不顺手重构、不重排 import、不全文格式化、不改无关命名
- 发现任务外的问题：记录并在交付时报告，不擅自修
- 死代码直接删，不注释掉（版本历史可找回）
- 不留调试代码（console.log / debug 分支），项目惯例允许的除外

## 风格

- 命名、缩进、引号、模块组织跟随当前文件与项目的既有风格
- 新代码读起来像周围代码，不擅自引入新范式、新工具函数、新目录结构

## 依赖与抽象

- 不为小事引入第三方依赖：先看现有依赖、标准库、几行手写能否解决
- 不过度设计：不加用不上的抽象层、配置项、参数、防御性检查
- 写新工具前先 grep 项目里是否已有同能力实现，避免重复造轮子

## 正确性

- 不确定的 API / 配置 / 类型签名：查源码或文档验证，禁止凭记忆编造
- 异常处理务实：吞异常必须注明原因；正常路径不包多余 try-catch
- 交付前跑项目可用的验证（lint / typecheck / build / test），以实际输出为准，不口头声称通过
