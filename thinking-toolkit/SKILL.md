# Thinking Toolkit · 结构化思维工具箱

## 概述

本技能整合 10 个结构化思维框架，覆盖「厘清问题→深度理解→验证决策→行动落地」全链路。AI 根据用户描述自动路由到最匹配的框架，用户无需记忆编号。

## 路由规则

收到用户输入后，按以下决策树判断该用哪个框架：

| 信号 | 路由到 |
|------|--------|
| 用户困惑、说不清问题是什么、卡住了 | 01 苏格拉底提问 |
| 用户想学概念、想理解某个东西 | 02 双层解释法 |
| 用户给出一个优秀范例想学习 | 03 反向拆解 |
| 用户要研究一个公司/产品/技术/行业 | 04 纵横分析法 |
| 用户想验证某个说法/数据/结论是否可信 | 05 事实核查 |
| 问题复杂需要多角度分析 | 06 专家会诊 |
| 现有方案越改越像打补丁、需要回到原点 | 07 第一性原理 |
| 本领域解法穷尽、想从别处借灵感 | 08 跨领域借解 |
| 两个选项都说得通、无法决断 | 09 双向钢人论证 |
| 纸上推演到极限、需要真实反馈 | 10 最小实验 |

**路由行为：**
1. 自动匹配后，先用一句话告知用户选择了哪个框架及原因
2. 用户确认或直接继续 → 执行该框架
3. 用户说「换一个」或指定其他框架 → 切换
4. 如果用户明确说出框架名（如「用第一性原理」），直接进对应流程，不多问

**前端开发者常见场景映射：**
- PM 需求模糊 → 01
- 学新框架/API/概念 → 02
- 看到优秀开源项目想学架构 → 03
- 评估某个库/框架/工具链 → 04
- 网上看到性能对比数据 → 05
- 复杂系统设计涉及多维度 → 06
- 老代码越改越烂要重构 → 07
- 性能/体验优化卡住 → 08
- 技术选型纠结 → 09
- 想验证某个技术方案是否可行 → 10

## 框架 01 · 苏格拉底提问

**目的：** 帮用户找到真正值得回答的问题。

**执行流程：**

1. 让用户描述困惑：发生了什么、怎么理解、卡在哪里
2. 进行最多 6 轮追问，遵守以下规则：
   - 每次只问一个问题，根据回答决定下一问
   - 区分用户说的是：可验证事实 / 对事实的解释 / 价值判断 / 希望实现的目标
   - 检查关键词是否含糊、默认了哪些前提、证据来源、有无相反解释、结论成立或不成立分别意味着什么
   - 每次提问前用一句话说明上一条回答让你更新了什么判断
   - 只问可能改变结论的问题，信息足够时立刻停止
3. 问诊结束后整理输出：
   - 用户最开始问的问题
   - 真正想解决的问题
   - 已确认的事实
   - 仍未验证的假设
   - 最可能改变结论的关键变量
   - 一个准确、具体、可继续行动的新问题
4. 等用户确认新问题后，再给出判断、理由和下一步行动

## 框架 02 · 双层解释法

**目的：** 同时给出小白版与专业版解释，确认用户是真懂还是只记住了类比。

**执行流程：**

1. 确认用户想学习的概念或问题
2. 输出两层解释：
   - **第一层（小白版）：** 用生活化语言和一个具体例子，让完全没有基础的人也能听懂
   - **第二层（专业版）：** 使用准确术语，讲清核心机制、适用边界和常见误解
3. 整理输出：
   - 小白说法与专业术语的对应关系
   - 最容易理解错的地方
   - 3 个用于检查是否真正理解的问题

## 框架 03 · 反向拆解

**目的：** 从优秀范例中提炼可复用规律。

**执行流程：**

1. 让用户提供想拆解的范例（产品页面、网页、方案、流程、数据看板或其他成品）
2. 确认用户想从中学到什么
3. 先用一句话说明它解决了什么问题，再反向拆解它为什么有效，重点分析：
   - 它服务谁，目标是什么
   - 采用了什么结构或流程
   - 哪些关键选择拉开了质量差距
   - 它的完成标准是什么
   - 哪些规律可以迁移，哪些细节只适合这个案例
4. 最终输出：
   - 3-5 条可复用规律
   - 一份可照着执行的操作清单
   - 一个最值得先尝试的小练习

## 框架 04 · 纵横分析法

**目的：** 对研究对象做可追溯的深度研究——纵看演化路径，横看竞品差异。

**执行流程：**

1. 确认研究对象（产品、公司、人物、技术、行业或事件）
2. 研究截止时间为执行当天
3. **纵向分析：**
   - 在什么背景和需求下诞生，关键推动者是谁
   - 经历了哪些重要转折、成功和失败
   - 哪些早期选择变成了今天的能力、路径依赖或包袱
4. **横向分析：**
   - 选择最值得比较的对象并说明原因
   - 用统一维度比较各自的强项、短板和独特性
   - 解释用户/客户/市场为什么选择它，又为什么放弃它
5. **交叉判断：**
   - 过去形成的能力、路径依赖和约束会怎样影响未来
   - 未来最可能出现哪 3 条路径
   - 每条路径出现的前提和预警信号
6. **证据规则：**
   - 优先使用官方资料、原始数据、论文、财报和访谈等一手来源
   - 重要结论就近标注来源与日期
   - 事实、推断和观点分开写
   - 冲突信息并列呈现，找不到证据时明确写"暂未核实"
7. **输出顺序：** 核心结论 → 关键时间线 → 横向对比表 → 详细分析 → 未来判断 → 仍待确认的问题
8. 报告 10000-30000 字，语言通俗，不堆砌资料

**注意：** 此框架需要联网搜索能力，执行时应主动使用 WebSearch 获取最新信息。

## 框架 05 · 事实核查

**目的：** 拆开事实，判断可信程度。

**执行流程：**

1. 让用户提供要核查的说法（观点、结论、数据或方案）
2. 先拆成三部分：
   - 可被外部验证的事实
   - 从事实推出的结论
   - 其中包含的价值判断
3. 对事实部分联网核查来源、样本、时间和完整上下文，标记为：
   - 已证实 / 基本成立但需收窄 / 存在争议 / 证据不足 / 明显错误
4. 在假设相关事实成立的情况下，检查：
   - 事实能否推出当前结论
   - 是否藏着未经验证的假设
   - 是否混淆相关性和因果关系
   - 是否遗漏了其他解释或关键信息
   - 结论在什么条件下成立或失效
5. 最终输出：
   - 哪些事实可信，哪些需要修正
   - 推理链中最关键的漏洞
   - 补强后的最合理版本
   - 用户目前可以相信到什么程度

**注意：** 此框架需要联网搜索能力来核查事实。

## 框架 06 · 专家会诊

**目的：** 让互补视角互相质疑再综合，找到真正的信息。

**执行流程：**

1. 让用户描述问题、已知事实、目标和现实约束
2. 为这个问题选择 3 种真正互补的专业视角，说明每种视角为什么必要
3. 让每种视角分别回答：
   - 它怎样重新定义这个问题
   - 最推荐的解决路径
   - 其他视角最容易忽略的风险
   - 什么新证据会让它改变判断
4. 让三种视角互相质疑，找出：
   - 共同认可的事实
   - 真正的分歧
   - 分歧背后的不同假设
5. 综合输出：
   - 综合后最推荐的方案
   - 适用条件
   - 最大风险
   - 退出条件
   - 第一步行动

**规则：** 不选择三个高度相似的身份，不模仿或编造真实人物的观点。信息不足时，先只问一个最关键的问题。

## 框架 07 · 第一性原理

**目的：** 拆回本质，重新推导路径。

**执行流程：**

1. 让用户描述想解决的问题
2. 用第一性原理把它拆回最底层，区分：
   - 已确认、无法绕开的基本事实
   - 习惯性接受、却没有验证过的假设
   - 真正想实现的目标
   - 现实中的资源与约束
3. 暂时放下行业惯例和现成方案，只从基本事实、目标和约束出发重新推导可行路径
4. 最终输出：
   - 原方案中只在修补表面的部分
   - 从基本事实重新推导出的新路径
   - 这条路径成立的前提
   - 验证它的第一步

## 框架 08 · 跨领域借解

**目的：** 从其他领域借来相通解法。

**执行流程：**

1. 让用户说明背景、当前做法、现实约束和具体卡点
2. 剥掉行业术语，抽象成底层结构，找出：
   - 问题的底层结构
   - 真正的核心矛盾
   - 普通解法失效的原因
3. 从历史案例以及至少 3 个彼此距离较远的领域中，每个案例说明：
   - 那个领域遇到了什么问题
   - 使用了什么解决机制
   - 与用户的问题相似在哪里
   - 哪些部分可以迁移
   - 什么条件下会失效
4. 选出最值得借用的 3 种机制，翻译成适合用户当前处境的解决方案
5. 推荐一个最值得先试的低成本、可逆实验

## 框架 09 · 双向钢人论证

**目的：** 两边都有道理时，先把两边说到最强再决断。

**执行流程：**

1. 让用户写清问题、两个选项、目标和现实约束
2. 先做一次双向钢人论证：
   - 用最完整有力的方式重述用户真正需要做出的选择
   - 分别给出支持两个方向的最强理由、适用条件、最大收益、最大风险，以及最难回答的反对意见
   - 找出双方真正的分歧、最可能改变结论的关键变量，以及还需要补充的信息
3. 只问用户一个最可能改变结论的问题
4. 等用户回答后，给出明确判断、理由、适用条件和下一步行动

**规则：** 不默认用户已把问题想清楚。如果发现问题本身定义有误，先重新定义。

## 框架 10 · 最小实验

**目的：** 用现实反馈替代空想。

**执行流程：**

1. 让用户描述正在纠结的选择或想法
2. 找出这个决定背后最需要验证的 3 个假设
3. 选出最可能改变最终结论的那一个
4. 围绕这个假设设计一个低成本、可逆、能在 7 天（或用户能接受的周期）内完成的最小实验
5. 写清：
   - 具体要做什么
   - 需要投入多少时间和资源
   - 观察什么指标
   - 什么结果支持继续
   - 什么结果提醒停止
   - 实验结束后能获得什么新信息
6. 告诉用户明天就能开始的第一个动作是什么

## 输出规范

- 每个框架执行完毕后，输出一份结构化结果（markdown 格式）
- 如果内容超过 2000 字，保存为文件并提供链接
- 语言风格：通俗直接，不堆砌术语，不写空话套话
- 对于需要联网的框架（04、05），主动使用 WebSearch 获取信息

## Pitfalls

- 不要在用户还没描述完问题时就急着选框架
- 路由判断错误时，用户说「不对」或「换一个」要立即切换，不要争辩
- 框架 01、09、10 是交互式流程（需要等用户回答再继续），不要一次性输出全部问题
- 框架 04 和 05 需要联网，如果搜索能力不可用，明确告知用户而非编造信息
- 不要在同一轮对话中混用多个框架，一次只用一个

## Verification

执行完毕后自检：
1. 是否按照对应框架的完整流程走完
2. 输出是否覆盖了框架要求的所有字段
3. 语言是否通俗、无 AI 腔（排比句、金句总结、"从来不是…而是…"）
