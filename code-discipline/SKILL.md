# AI 编码纪律

每次写代码、改代码时对照执行，交付前自查一遍。全部为硬约束；与用户当次明确指令冲突时，用户指令优先。

## 注释

- 只写代码本身表达不了的信息（为什么这么做、约束、坑、防回退提醒），一行内说清
- 禁止复述代码逻辑、改动过程说明式注释、多处重复同一说明
- 注释与代码一律不加 emoji；注释密度跟随周围代码

## 改动范围

- 只改任务要求的代码；不顺手重构、不重排 import、不全文格式化、不改无关命名
- 发现任务外的问题：记录并在交付时报告，不擅自修
- 死代码直接删，不注释掉（版本历史可找回）
- 不留调试代码（console.log / debug 分支），项目惯例允许的除外

## 风格

- 命名、缩进、引号、模块组织跟随当前文件与项目的既有风格
- 新代码读起来像周围代码，不擅自引入新范式、新工具函数、新目录结构

## 依赖与抽象

- 不为小事引入第三方依赖：先看现有依赖、标准库、几行手写能否解决
- 不过度设计：不加用不上的抽象层、配置项、参数、防御性检查
- 写新工具前先 grep 项目里是否已有同能力实现，避免重复造轮子

## 正确性

- 不确定的 API / 配置 / 类型签名：查源码或文档验证，禁止凭记忆编造
- 异常处理务实：吞异常必须注明原因；正常路径不包多余 try-catch
- 交付前跑项目可用的验证（lint / typecheck / build / test），以实际输出为准，不口头声称通过

## 可移植性（通用产物）

通用 skill、跨项目脚本、文档示例等换个环境就要能用的产物：
- 正文与示例禁止出现本机特定信息：用户绝对路径（~/work/... 之类）、机器特定的工具与生成命令；本机增强入口放全局记忆或环境配置层，skill 只写通用查找逻辑
- 跨平台成立：命令给三平台等价或注明平台限定（Windows 注意 .cmd shim、路径分隔符、行长限制）；只适配当前开发机视同未完成
- 跨 shell 成立：可跨 shell 的脚本用 POSIX 写法，禁用分词依赖（zsh 默认不对 $VAR 拆词，`for x in $LIST` 整串单元素）与 bash 专属语法（关联数组 declare -A）；多元素迭代用 while read 逐行读
- 声明的兼容范围（平台 / Node 版本）必须实测验证，不得想当然承诺
- 通用脚本住 skill 目录内跨项目直调，不复制进项目；目标路径相对用户 cwd 解析

## 自迭代（经验沉淀）

出现以下信号时，把经验沉淀进对应 skill，让同类错误只犯一次：
- 被用户明确纠正了做法
- 踩坑返工，且根因是可复用的认知缺失
- 验证了新的通用做法，现有 skill 未覆盖

流程：
1. 归属判断：编码纪律 → 本 skill；交互偏好 → 走全局记忆，不进 skill；其他领域 → 按名称/关键词在已安装 skill 清单中匹配定位，匹配不到时问用户，不猜
2. 最小增量更新：只追加条目或坑注记，不重写结构；超过 5 行的细节放 references/
3. 版本与提交：bump 版本（新增规则 minor、措辞修正 patch）；在 skill 所在 git 仓库提交（`git rev-parse --show-toplevel` 从 skill 路径定位仓库）；个人通用 skill 仓可直接 push，业务 skill 仓只 commit 不 push（push 牵动发版，用户要求时再推）
4. 交付时报告更新了哪个 skill 哪条规则，git 历史可回滚

不沉淀：一次性问题、项目特定细节（进项目记忆）、未验证的猜测、用户明说不用记的
